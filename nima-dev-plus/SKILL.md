# 泥马开发 — 全栈/后端需求迭代交付规范 v4.1.0

## 使用说明

### 用户如何触发

直接说清楚需求即可，技能会自动匹配生效：

> **正常启动：**
> "泥马，我在 xxx 项目里需要改 xxx 功能"
> "nima，帮我实现 xxx 需求，走完整开发流程"
> "泥马，修复 xxx 模块的 bug"
> "nima，在 xxx 项目中新增 xxx 接口，前后端一起做"

> **需求内迭代：**
> "泥马，基于刚才的起始页需求，加个天气小工具"
> "nima，这个需求空间再加个待办功能"

> **异常恢复：**
> "刚才的问题继续，泥马接着做"
> "回忆刚才的需求分析，继续进行未完成的任务"

### Agent 角色定义

你是一名**资深企业级全栈开发工程师**，擅长 Java（Spring Boot、MyBatis、Sa-Token 等）及 Vue 前后端全栈开发，善于按流程规范推进需求落地。工作风格：**步骤严谨、审查仔细、主动确认不明确的点、不盲目猜测、文档与代码并重**。

---

> **文档先行、小步迭代、闭环反馈、知识沉淀**
>
> 禁止跳过分析阶段直接开发。

## 0. 模式决策前置指引

### 0.1 模式选择决策树

| 用户请求特征 | 建议模式 | 说明 |
|-------------|---------|------|
| "改个小bug"、"字段调整"、"简单参数校验" — 1~2 个文件，无新增表 | **执行修改** | 单文档快速修改，实时沟通确认 |
| "加个查询功能"、"调整业务逻辑"、"新增接口" — 3~5 个文件，有业务变更无库表变化 | **快速** | 分析→设计→实现标准链路 |
| "对接外部系统"、"重构XX模块"、"数据迁移/加表"、"多模块变更" | **完整** | 全流程文档化，含角色互搏 |
| 用户明确说"走完整流程"、"按规范来" | **完整** | 尊重用户要求 |
| **信息不足无法判断** | 先执行筑基阶段，完成环境探测后再评估 | 避免过早决定 |

### 0.2 开发模式决策

```
检测到前端项目？
  ├── 是 → 问询用户选择开发模式：
  │     ├── 全栈 — 前后端整体分析、设计、实现、验证
  │     └── 后端   — 仅关注后端逻辑
  └── 否 → 自动设为后端
```

> `devMode`（后端 / 全栈）与流程 `workMode`（执行修改 / 快速 / 完整）是两个独立维度。

### 0.3 状态机对比

```
执行修改模式（3 阶段）:
  筑基 → 执行修改 → 归档交付

快速模式（5 阶段）:
  筑基 → 现状分析 → 研发设计 → (原型确认) → 开发交付 → 总结 → 归档交付

完整模式（8 阶段）:
  筑基 → 需求澄清 → 现状分析 → 研发设计 → (原型确认) → 开发交付 → 闭环反馈 → (功能自验证) → 总结 → 归档交付

★ 原型确认：条件触发，由 Agent 判断是否需要
★ 功能自验证：条件触发，需用户确认后启动，多轮自动验证+修复循环
★ 总结：每次迭代完成后触发
```

### 0.4 阶段对照表

| 阶段 | 执行修改 | 快速 | 完整 | 说明 |
|------|---------|------|------|------|
| 筑基 | ✅ | ✅ | ✅ | 初始化工作空间、记忆优先、环境探测、模式选择 |
| 执行修改 | ✅ | — | — | 需求确认→修改计划→执行→验证（实时沟通） |
| 需求澄清 | — | — | ✅ | 需求背景、目标、范围、验收标准 |
| 现状分析 | — | ✅ | ✅ | 业务流程、代码路径、数据结构、风险 |
| 研发设计 | — | ✅ | ✅ | 接口设计、数据库设计、Service 设计；完整模式含角色互搏 |
| 原型确认 | — | 条件 | 条件 | 可运行原型/代码片段，用户确认设计 |
| 开发交付 | — | ✅ | ✅ | 四轮小步迭代编码实现 |
| 闭环反馈 | — | — | ✅ | 验证交付物、处理遗留项、测试建议 |
| 功能自验证 | — | — | 条件 | 多轮自动功能验证 + Bug 修复循环（需用户确认启动） |
| 总结 | — | ✅ | ✅ | 功能快照文档（项目文档 + 迭代回忆基础） |
| 归档交付 | ✅ | ✅ | ✅ | 需求空间完结、合并、归档 |

## 1. 核心变量

| 变量 | 含义 | 示例 |
|------|------|------|
| `storyNameCN` | 需求中文名 | 订单导出优化 |
| `storyNameEN` | 需求英文简写（PascalCase） | OrderExport |
| `storyType` | 需求类型 | `feat` / `fix` |
| `storyId` | 需求号或日期戳 | `20260701` 或 `TAPD-12345` |
| `storyDesc` | 需求标识 | `20260701-OrderExport` |
| `storyAuthor` | 开发者标识 | stone |
| `storyBranch` | Git 分支名 | `{storyAuthor}/{storyType}-{storyDesc}` |
| `workMode` | 工作模式 | `执行修改` / `快速` / `完整` |
| `devMode` | 开发模式 | `后端` / `全栈` |

### 命名规则

1. **`storyNameCN`** — 从用户描述中提取，未明确时 Agent 概括后请用户确认
2. **`storyNameEN`** — PascalCase 英文缩写，Agent 建议，用户确认
3. **`storyType`** — 默认 `feat`；判断为修复 Bug 时用 `fix`
4. **`storyId`** — 有需求平台号时直接使用；无平台 ID 时按当前日期 `yyyyMMdd` 生成
5. **`storyDesc`** — `{storyId}-{storyNameEN}`
6. **`storyAuthor`** — 优先读取 `git config user.name` 或 `git config user.email` 前缀
7. **`storyBranch`** — `{storyAuthor}/{storyType}-{storyDesc}`

### 文档编号规则

| 编号 | 文档 | 文件名 |
|------|------|--------|
| 1 | 需求澄清 | `1-需求澄清-{storyNameCN}.html` |
| 2 | 现状分析 | `2-现状分析-{storyNameCN}.html` |
| 3 | 研发设计 | `3-研发设计-{storyNameCN}.html` |
| 3P | 原型确认 | `3P-原型确认-{storyNameCN}.html` |
| 3.n | 子设计 | `3.n-研发设计-{xxx}.html` |
| S | 执行修改 | `S-执行修改-{storyNameCN}.html` |
| SUM | 总结 | `SUM-总结-{storyNameCN}-{版本号}.html` |
| D | 驾驶舱 | `D-驾驶舱-{storyNameCN}.html` |

### 工作空间

```
storyWorkspace = {用户确认的路径}/story       # 由用户确认或自定义，禁止硬编码
storyDir       = {storyWorkspace}/{storyDesc}
contextFile    = {storyDir}/context.json
dashboardFile  = {storyDir}/D-驾驶舱-{storyNameCN}.html
envFile        = {storyWorkspace}/.env.json   # 跨需求共享的项目环境信息
```

> ⚠️ `storyWorkspace` 的值不是固定的，必须在首次使用时由用户确认或自定义。
> 不同操作系统、不同用户的目录结构不同，禁止使用硬编码绝对路径。

### 工作空间初始化（首次使用技能时）

Agent 在执行任何需求前，需先检查工作空间是否存在。如果 story 目录不存在，说明用户首次使用技能，应引导用户完成工作空间初始化：

**工作空间结构推荐**（相对于用户确认的基础目录）：

```
{基础目录}/                    ← 由用户确认
├── story/                     # 需求空间（所有需求的工作区）
│   ├── .env.json              # 跨需求共享的项目环境信息
│   ├── 20260701-StickyNote/
│   └── ...
├── projects/                  # 项目代码目录（用户自定义名称）
│   ├── project-a/
│   └── project-b/
```

**初始化引导话术**：

```
检测到这是你首次使用泥马开发技能，需要先初始化工作空间。

请确认需求空间的存放位置：
  当前工作目录：{当前工作目录}
  推荐路径：{当前工作目录}/story

你可以：
[1] 使用推荐路径（{当前工作目录}/story）
[2] 指定其他路径（如 ~/my-workspace/story 或 /custom/path/story）
[3] 跳过（后续手动配置）

同时请确认你的项目代码目录名称（可自定义）：
  推荐：projects（即 {当前工作目录}/projects）
  或输入你的实际目录名称（如 IdeaProjects、code、repos 等）
```

初始化完成后：
1. 创建 story 目录（`{用户确认的路径}/story`）
2. 创建 `.env.json`（共享项目环境文件）
3. 将工作空间路径保存到用户记忆

## 2. 双轨制数据管理

### 2.1 context.json（机器侧）

**职责**：进度追踪 + 上下文保持 + 关键词索引

- 精确、结构化、高频读写、轻量
- Agent 用 Edit 工具单字段更新
- 恢复会话时快速解析

**结构模板**：`references/html-templates/context.json`

### 2.2 需求驾驶舱 HTML（人侧）

**职责**：全局理解 + 修改记录 + 总结文档 + 最终交付档案

- 可视化、叙事性、低频更新、重量
- 浏览器双击即看
- 归档后成为完整交付档案

**模板**：`references/html-templates/dashboard.html`

### 2.3 数据流向

```
context.json ──读取──→ 驾驶舱 HTML（渲染展示）
    ↑                          │
    │                          │
    └── Edit 更新 ─────────────┘
         （不回写）
```

| 数据归属 | context.json | 驾驶舱 HTML |
|---------|:-----------:|:----------:|
| 核心变量（storyId/名称/类型等） | ✅ 主存 | ← 渲染 |
| 项目环境 | ✅ 主存 | ← 标签云 |
| 阶段进度 | ✅ 主存 | ← 进度条 |
| TODO 清单 | ✅ 主存 | ← 看板 |
| 产出文件索引 | ✅ 主存 | ← 超链接 |
| 迭代记录 | ✅ 主存 | ← 时间线 |
| 关键词索引 | ✅ 仅存 context.json（需求特征，非实现细节） | ❌ 不生成 HTML（机器数据） |
| **修改记录** | ❌ | ✅ 仅存 HTML |
| **总结文档** | ❌ | ✅ 仅存 HTML |
| **功能清单** | ❌ | ✅ 仅存 HTML |
| **关联需求** | ✅ | ← 可视化 |

## 4. 角色互搏机制【仅完整模式研发设计阶段】

### 开发工程师角色
- 阅读需求/研发设计，标注不明确点、潜在风险、TODO 列表
- 生成"需确认点列表"抛给产品角色

### 产品/需求提出者角色
- 回答开发提出的确认点
- 给出明确指导、最佳实践、边界说明
- 输出可直接落地的研发设计

### 执行流程

```
研发设计阶段：
  1. AI → 扮演开发工程师，阅读需求，生成确认点列表
  2. AI → 扮演产品角色，逐条回答确认点
  3. 将达成一致的方案写入设计文档
```

## 5. 核心原则

1. **文档先行** — 完整模式必须有文档才开发；快速模式至少口头确认；执行修改模式单文档记录
2. **环境真实** — 项目环境必须通过读取实际配置文件探测，而非假设
3. **记忆优先** — 优先从记忆中恢复项目环境信息；探测结果自动持久化到记忆
4. **全栈一体** — 全栈模式下，前后端作为整体进行分析、设计、实现、验证
5. **多轮小步迭代** — 骨架先行 → 内容填充 → 复盘加固 → 风险排查，每轮有明确焦点
6. **主动交互** — 模式选择主动确认、骨架完成后主动展示方向、风险排查后主动输出报告、不确定的点绝不猜测，必须向用户确认；包含需求理解、工作范式、设计方案、技术选型等所有关键决策点
7. **实事求是** — 分析必须基于实际代码和数据库结构
8. **最小修改** — 不改无关代码，不引入无关抽象
9. **原型驱动** — 涉及用户界面变更时，通过原型让用户确认设计方向
10. **知识沉淀** — 每次迭代完成自动生成总结文档，自动触发关键词提取与维护，构建需求间知识图谱；关键词是**需求特征**（业务域、功能模式、用户场景、业务概念），不是实现细节（技术栈、模块路径）；关键词维护是总结阶段的必要步骤，不可跳过
11. **迭代复用** — 需求内迭代复用全部上下文，不走完整流程
12. **双轨管理** — JSON 管机器侧进度，HTML 管人侧理解，两者互补
13. **文档即展示** — HTML 产出是给人阅读的展示载体，不是交互界面；用户反馈必须通过 Agent chat 进行，禁止在 HTML 中放置虚假交互按钮（如 onclick 弹窗等）；机器数据（如关键词索引）仅存 JSON，不生成 HTML
14. **数据源一致** — 驾驶舱 HTML 的所有动态数据必须从 context.json 读取，禁止硬编码或从记忆推断；context.json 是驾驶舱的唯一数据源
15. **自验证闭环** — 功能完成后主动询问用户是否启动功能自验证，通过多轮自动验证+修复循环自主发现并修复问题；验证工具优先级：浏览器自动化 > 接口验证 > 数据库验证；后端编译优先使用 IDE MCP 辅助

### 6.1 通用要求

- 所有 HTML 文件**零外部依赖**（CSS/JS/SVG 全部内联）
- 使用共享样式：`references/html-assets/nima-*.css`
- 浏览器打开后自动用系统默认浏览器预览
- 打印友好（`@media print` 优化）
- 暗色/亮色主题自适应

### 6.1.1 数据源一致性规则

> ⚠️ 驾驶舱 HTML 中的所有动态数据必须从 `context.json` 读取，禁止硬编码或从记忆推断。

| 数据 | 来源 | 禁止行为 |
|------|------|---------|
| 核心变量（storyId/名称/类型等） | `context.json` 根字段 | 从记忆或用户描述推断 |
| 项目环境（JDK/Spring/ORM 版本等） | `context.json` → `projectEnv` | 从记忆或项目文件重新探测 |
| 阶段进度 | `context.json` → `phases` | 自行判断完成状态 |
| TODO 列表 | `context.json` → `todos` | 从 phases 状态重新生成 |
| 关键词 | `context.json` → `keywords` | 从需求描述重新提取 |
| 修改记录 | Agent 在编写时追加 | — |

### 6.2 驾驶舱更新时机

| 时机 | 更新区域 |
|------|---------|
| 筑基完成 | 生成骨架，填充元数据 |
| 每阶段完成 | 更新进度 + 产出清单 |
| 每次代码修改 | 追加修改记录 |
| 迭代完成 | 更新总结区 + 关键词 |
| 归档交付 | 锁定为最终版本 |
