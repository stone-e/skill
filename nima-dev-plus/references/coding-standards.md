# 泥马开发 — 增量编码规范

> 本文件定义了泥马开发技能特有的编码规范，通用规范遵循项目 `~/.claude/CLAUDE.md` 中的规则。
> 本文件仅记录**增量内容**（CLAUDE.md 中未覆盖的或泥马特有的约束）。

---

## 一、泥马特有规范

### 1.1 HTML 产出规范

- 所有 HTML 文件必须**零外部依赖**（CSS/JS/SVG 全部内联）
- 必须支持响应式布局（桌面/平板/打印）
- 必须支持暗色/亮色主题自适应（`prefers-color-scheme`）
- 代码块必须有语法高亮
- 原型页面必须有交互标注和操作栏

### 1.2 驾驶舱更新规范

- 每阶段完成后必须更新驾驶舱 HTML
- 修改记录按时间倒序排列
- TODO 看板必须与 context.json 的 todos 保持同步
- 进度百分比 = 已完成阶段数 / 总阶段数 × 100

### 1.3 双轨制数据一致性

- context.json 是机器侧唯一数据源
- 驾驶舱 HTML 是 context.json 的可视化展示
- HTML → JSON 不回写
- 修改记录、总结文档、关键词索引仅存在于 HTML

### 1.4 原型确认规范

- 原型 HTML 必须包含顶部标注横幅
- 可交互元素必须有虚线框高亮
- 底部必须有固定操作栏（确认/修改）
- 生成后自动用系统浏览器打开

### 1.5 SQL 文件存放规范

- 数据库变更 SQL 存放在 `{storyDir}/sql/` 目录
- 文件命名：`{表名}.sql`（如 `sticky_note.sql`）
- SQL 文件头部需包含注释：需求名、作者、日期
- 仅适用于完整模式或涉及数据库变更的快速模式

### 1.6 功能自验证规范

#### 1.6.1 验证环境准备

- 前端项目启动：`npm run dev` / `pnpm dev`，确认端口监听
- 后端项目启动：优先使用 IDE MCP `build_project` + `execute_run_configuration`
- 运行时信息记录到 `context.json` 的 `projectRuntime` 字段

#### 1.6.2 验证工具优先级

| 优先级 | 工具 | 用途 |
|--------|------|------|
| 1 | `mcp__agent-browser__*` | 浏览器自动化验证（首选） |
| 2 | `mcp__plugin_playwright_playwright__*` | Playwright 浏览器验证 |
| 3 | `Bash` (curl) | 接口自主验证 |
| 4 | `mcp__MySQL-*` | 数据库验证 |

#### 1.6.3 截图与证据

- 每步操作后截图保存到 `{storyDir}/verification/round-{n}-step-{m}.png`
- 发现问题时截图作为 Bug 证据
- 截图文件名格式：`round-{轮次}-step-{步骤}-{描述}.png`

#### 1.6.4 Bug 记录规范

- Bug ID 格式：`BUG-{三位序号}`
- 严重级别：`high`（功能不可用）/ `medium`（功能异常但可用）/ `low`（体验问题）
- 类型：`functional` / `ui` / `api` / `data`
- 必须包含：复现步骤、预期结果、实际结果、截图路径

#### 1.6.5 验证通过标准

- 所有验收标准通过
- 无 high/medium 级别 Bug
- 边界场景处理正确
- 异常场景处理正确

### 1.7 TODO 看板渲染规范

驾驶舱 HTML 的 TODO 看板必须遵循以下规则，防止重复渲染：

- **数据源唯一**：仅从 `context.json` 的 `todos` 数组读取
- **不重复 phases**：不要将 phases 的完成状态再次渲染为 TODO 项
- **空状态处理**：如果 `todos` 为空数组，显示"暂无待办"而非空白或占位
- **不生成空标签**：不要生成空的 `</tbody></table>` 等残留标签

**正确做法**：
```html
<!-- 从 context.json 的 todos 数组渲染 -->
<div class="todo-item done"><span class="todo-status">✅</span><span class="todo-text">需求澄清</span></div>
<div class="todo-item"><span class="todo-status">⬜</span><span class="todo-text">现状分析</span></div>
```

**错误做法**：
```html
<!-- ❌ 不要把 phases 的完成状态再渲染一遍 -->
<div class="todo-item done">✅ 筑基</div>
<div class="todo-item done">✅ 需求澄清</div>
<!-- ❌ 不要生成空占位 -->
</tbody></table>
```

### 1.8 修改记录格式规范

驾驶舱 HTML 中的修改记录按以下格式追加：

```html
<div class="changelog-entry">
  <span class="changelog-time">{YYYY-MM-DD HH:mm}</span>
  <span class="changelog-author {ai|用户名}">{作者}</span>
  <span class="changelog-action">{修改描述}</span>
</div>
```

- 按时间倒序排列（最新在前）
- `changelog-author` 类：用户操作用用户名，AI 自动操作用 `ai`
- 里程碑事件（阶段完成）添加 `milestone` 类

### 1.9 关键词维护规范

#### 1.9.1 关键词的本质

关键词是给 Agent 做**需求知识图谱查询**用的机器数据，目的是：
- 未来做同类需求时，快速定位需求背景和关联知识
- 帮助 Agent 在筑基阶段发现关联需求并吸收上下文

#### 1.9.2 关键词维度（需求特征，非实现细节）

| 维度 | 含义 | 应该包含 | 不应该包含 |
|------|------|---------|-----------|
| `domain` | 业务域 | 起始页、工作台、订单管理、审批流 | {项目技术名}、{模块名} |
| `pattern` | 功能模式 | 工具嵌入、弹窗交互、实时保存、数据导出、批量操作 | 防抖、Composable、JWT认证 |
| `scenario` | 用户场景 | 个人效率、快速操作、轻量记录、数据录入 | 用户隔离、权限校验 |
| `concept` | 业务概念 | 便签、发票、审批、报表、工单 | StickyNote、Invoice |

#### 1.9.3 正确 vs 错误示范

**✅ 正确**（StickyNote 需求）：
```json
{
  "domain": ["起始页", "工作台"],
  "pattern": ["工具嵌入", "弹窗交互", "实时保存"],
  "scenario": ["个人效率", "快速备忘", "信息记录"],
  "concept": ["便签", "备忘", "快捷工具"]
}
```

**❌ 错误**（StickyNote 需求 — 含实现细节）：
```json
{
  "domain": ["起始页", "工作台", "门户"],
  "pattern": ["工具嵌入", "弹窗交互", "实时保存", "用户配置隔离"],
  "scenario": ["个人效率", "快速备忘", "信息记录"],
  "concept": ["便签", "StickyNote", "CRUD"]
}
```

**错误分析**：
- `"门户"` → 太宽泛，几乎每个门户需求都会匹配
- `"用户配置隔离"` → 技术方案，不是功能模式
- `"StickyNote"` → 英文类名，不是业务概念
- `"CRUD"` → 技术概念，不是业务概念

#### 1.9.4 关键词质量检查清单

提取关键词前，用以下问题自检：

| 检查项 | 通过标准 |
|--------|---------|
| 技术栈检查 | 不包含 Vue3/React/Spring/JWT/MyBatis 等技术名词 |
| 路径检查 | 不包含 {项目技术名} 等项目路径 |
| 类名检查 | 不包含 StickyNote/Invoice 等英文类名 |
| 实现检查 | 不包含 防抖/节流/CRUD/Composable 等实现细节 |
| 价值检查 | 每个关键词能否帮助未来 Agent 判断"这是否是同类需求"？ |
| 区分度检查 | 关键词组合是否能区分本需求与其他需求？ |

#### 1.9.5 维护时机

- 每次迭代完成后必须更新 `context.json` 的 `keywords` 字段
- 新需求筑基阶段必须搜索已有 `context.json` 的 `keywords` 做关联匹配
- 关键词仅存 `context.json`，不生成独立 HTML

## 三、多轮小步迭代规范（泥马细化）

### 3.1 迭代与阶段的区别

| 概念 | 粒度 | 说明 |
|------|------|------|
| **阶段** | 粗 | 筑基、现状分析、研发设计、开发交付等 |
| **迭代** | 细 | 开发交付内的第1-4轮，或需求内迭代 |
| **需求内迭代** | 中 | 同一需求空间内的功能追加 |

### 3.2 开发交付四轮迭代

```
第1轮 骨架先行     │ 搭方法框架（可伪代码）→ 验证流程 → 主动交互确认方向
第2轮 内容填充     │ 按项目习惯填充实现 → 串联检查 → 收口自查
第3轮 复盘验证     │ 重新理解需求 → 逐条覆盖验收标准 → 加固异常边界 → 编译验证
第4轮 风险排查     │ 扫描隐藏风险 → 冲突检查 → 输出报告给用户
```

### 3.3 需求内迭代简化规则

| 功能规模 | 简化策略 |
|---------|---------|
| 极小（加个字段、改个提示） | 直接修改 → 总结递增 |
| 小（加个小组件） | 轻量设计 → 开发交付（1-2轮）→ 总结递增 |
| 中等（加个新页面） | 轻量设计 → 原型确认 → 开发交付 → 总结递增 |
| 大（涉及多模块） | 建议拆分为新需求空间 |

## 四、总结文档规范

### 4.1 总结版本管理

- 初始需求完成 → 总结 v1
- 需求内迭代完成 → 总结 v2、v3...
- 归档交付时 → 最终总结（FINAL）

### 4.2 总结内容要求

- 功能清单必须标注每个功能属于哪个版本
- 技术架构必须包含目录结构和 API 清单
- 交付统计必须量化（文件数、代码行数、接口数等）
- 已知限制必须明确标注

## 五、异常处理规范（泥马特有）

### 5.1 HTML 生成异常

| 异常 | 处理 |
|------|------|
| CSS 内联后文件过大 | 拆分共享 CSS 为内联 <style>，确保单文件 < 50KB |
| 浏览器打开失败 | 提示用户手动打开文件路径 |
| 模板变量未替换 | 生成前检查所有 `{variable}` 是否已填充 |

### 5.2 双轨数据不一致

| 异常 | 处理 |
|------|------|
| context.json 已更新但驾驶舱未更新 | 以 context.json 为准，重新渲染驾驶舱 |
| 驾驶舱显示与实际代码不符 | 以实际代码为准，更新 context.json 后重新渲染 |
