# 需求内迭代

## 目标

在已有需求空间内追加功能点，复用全部上下文和记忆，不走完整流程。

## 触发条件

用户说以下类似表述时触发：
- "基于这个需求，加个 xxx"
- "再追加一个 xxx 功能"
- "这个需求空间再加个 xxx"
- "在刚才的基础上，加个小工具"

## 核心原则

- **复用全部上下文**：项目环境、代码架构、记忆、封板文档
- **不走完整流程**：跳过需求澄清和现状分析（已有上下文）
- **轻量迭代**：只需关注新增功能点本身
- **总结递增**：每次迭代完成，总结文档递增版本

## 执行流程

```
触发需求内迭代
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│  步骤 1：确认迭代目标                                         │
│  - 与用户确认追加的功能点描述                                  │
│  - 评估改动范围（文件数、是否涉及数据库变更）                   │
│  - 更新 context.json 的 currentIteration                      │
└─────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│  步骤 2：轻量筑基                                             │
│  - 复用已有 projectEnv（无需重新探测）                         │
│  - 定位新增功能涉及的代码文件                                  │
│  - 阅读相关代码上下文                                         │
└─────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│  步骤 3：轻量研发设计                                         │
│  - 仅针对新增功能点设计                                       │
│  - 评估是否需要原型确认（同样遵循决策树）                       │
│  - 更新 TODO 列表                                            │
└─────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│  步骤 4：开发交付                                             │
│  - 四轮小步迭代（可简化为 1-2 轮，视功能大小）                  │
│  - 复用项目编码风格和工具类                                    │
└─────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│  步骤 5：总结递增                                             │
│  - 生成新版本总结文档                                         │
│  - 更新关键词索引                                             │
│  - 更新驾驶舱 HTML                                            │
└─────────────────────────────────────────────────────────────┘
    │
    ▼
  回到等待状态（用户可继续追加或归档交付）
```

## 简化规则

| 功能规模 | 简化策略 |
|---------|---------|
| **极小**（加个字段、改个提示） | 直接修改 → 总结递增，跳过设计和原型 |
| **小**（加个小组件、小工具） | 轻量设计 → 开发交付 → 总结递增 |
| **中等**（加个新页面、新接口） | 轻量设计 → 原型确认 → 开发交付 → 总结递增 |
| **大**（涉及多模块、数据库变更） | 建议拆分为新需求空间 |

## context.json 更新

```json
{
  "currentIteration": 3,
  "iterations": [
    ...,
    {
      "index": 2,
      "type": "iteration",
      "description": "追加待办事项小工具",
      "phases": {
        "筑基": { "done": true },
        "研发设计": { "done": false, "output": "" },
        "原型确认": { "done": false, "skipped": false },
        "开发交付": { "done": false },
        "闭环反馈": { "done": false }
      },
      "summary": null
    }
  ]
}
```

## 关键词维护

每次迭代完成后，Agent 应：
1. 提取新增功能涉及的**需求特征关键词**（业务域、功能模式、用户场景、业务概念）
2. 追加到 `context.json` 的 `keywords` 字段
3. 检查是否有关联需求需要更新 `relatedStories`

> 关键词是给 Agent 做知识图谱查询用的机器数据，仅存 context.json，不生成 HTML。
> 不要提取技术栈、模块路径等实现细节作为关键词。

## 退出迭代

用户说以下类似表述时，退出迭代，进入归档交付：
- "这个需求空间完结了"
- "归档交付"
- "这个需求做完了，提交吧"
- "没有要加的了"

## 完成后更新

- `context.json`：更新当前迭代状态，追加 `summary`
- `context.json`：追加新关键词到 `keywords` 字段
- 驾驶舱 HTML：更新迭代历史、功能清单、总结区
