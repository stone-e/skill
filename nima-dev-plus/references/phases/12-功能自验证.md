# 功能自验证 — 仅完整模式，条件触发

## 目标

通过多轮自动功能验证 + Bug 修复循环，自主发现并修复问题，直到功能验证通过。

## 触发条件

闭环反馈完成后，Agent 主动询问用户是否启动功能自验证。

## 前置条件

| 条件 | 说明 |
|------|------|
| 用户确认 | 必须经用户明确同意才能启动 |
| 多模态模型 | 提醒用户切换到支持图片理解的模型（用于浏览器验证） |
| 项目可运行 | 前端项目需可启动（`npm run dev` / `pnpm dev`） |
| 后端可编译 | 后端项目需可通过 IDE MCP 编译 |

---

## 执行流程总览

```
闭环反馈完成
    │
    ▼
Agent 主动询问：是否启动功能自验证？
    │
    ├── 用户拒绝 → 跳过，进入总结
    │
    └── 用户确认 → 提醒切换到多模态模型
              │
              ▼
        准备验证环境（启动项目、确认运行状态）
              │
              ▼
        ┌─────────────────────────────────────┐
        │         验证轮次循环                  │
        │                                      │
        │  第 N 轮验证                          │
        │    ├── 浏览器自主验证（前端功能）       │
        │    ├── 接口自主验证（后端 API）         │
        │    ├── 记录发现的问题/Bug               │
        │    └── 判断：是否通过？                 │
        │         ├── 通过 → 退出循环             │
        │         └── 未通过 → 进入修复           │
        │              │                        │
        │              ▼                        │
        │  统一修复 Bug                          │
        │    ├── 分析 Bug 根因                    │
        │    ├── 制定修复方案                     │
        │    ├── 执行修复（修改代码）              │
        │    └── 后端编译验证（IDE MCP）           │
        │              │                        │
        │              ▼                        │
        │  重启项目                              │
        │    ├── 重启后端（IDE MCP）              │
        │    └── 确认前端热更新                   │
        │              │                        │
        │              ▼                        │
        │  进入第 N+1 轮验证 ←──────────────────│
        └─────────────────────────────────────┘
              │
              ▼
        所有验证通过 → 进入总结
```

## 步骤 1：主动询问与用户确认

闭环反馈完成后，Agent 向用户展示：

```
闭环反馈已完成，所有文档和代码已交付。

是否启动【功能自验证】？
功能自验证将自动：
  1. 启动项目（前端 + 后端）
  2. 使用浏览器工具自主操作和验证功能
  3. 使用接口工具自主验证 API
  4. 发现问题自动记录并修复
  5. 多轮验证直到全部通过

⚠️ 建议切换到多模态模型（支持图片理解），以便 Agent 截图分析页面效果。

请选择：
[1] 启动功能自验证
[2] 跳过，直接进入总结
```

## 步骤 2：准备验证环境

### 2.1 确认项目启动命令

从 `context.json` 的 `projectRuntime` 字段或项目配置中获取启动命令：

| 项目 | 命令来源 | 默认值 |
|------|---------|--------|
| 前端 | `package.json` → `scripts.dev` | `npm run dev` 或 `pnpm dev` |
| 后端 | IDE MCP → `build_project` | 通过 IntelliJ IDEA MCP |

### 2.2 启动前端项目

```bash
cd {frontendProjectPath}
{frontendCommand}
```

确认前端启动成功：
- 检查端口是否监听（默认 5173 / 3000）
- 记录 `frontendPid` 到 `context.json` 的 `projectRuntime`

### 2.3 启动后端项目

**优先使用 IDE MCP**（如果可用）：
```
mcp__jetbrains-idea__build_project → 编译项目
mcp__jetbrains-idea__execute_run_configuration → 启动项目
```

**备选方案**：
```bash
cd {backendProjectPath}
mvn spring-boot:run
```

确认后端启动成功：
- 检查端口是否监听（默认 8080 / 8100）
- 记录 `backendPid` 到 `context.json` 的 `projectRuntime`

### 2.4 记录运行时信息

更新 `context.json`：
```json
{
  "projectRuntime": {
    "backendCommand": "mvn spring-boot:run",
    "frontendCommand": "pnpm dev",
    "backendPort": 8080,
    "frontendPort": 5173,
    "backendPid": 12345,
    "frontendPid": 12346
  }
}
```

## 步骤 3：验证轮次循环

### 3.1 验证策略选择

根据需求类型选择验证方式：

| 需求类型 | 主要验证方式 | 辅助验证方式 |
|---------|------------|------------|
| 前端交互功能（如便签、弹窗） | 浏览器自主验证 | 接口验证 |
| 后端 API 功能 | 接口自主验证 | — |
| 全栈功能 | 浏览器 + 接口 | — |
| 纯后端逻辑 | 接口自主验证 | 数据库验证 |

### 3.2 浏览器自主验证

**可用工具**（按优先级）：
1. `mcp__agent-browser__*` — 浏览器自动化
2. `mcp__plugin_playwright_playwright__*` — Playwright 浏览器
3. `mcp__codegraph__*` — 代码分析辅助

**验证流程**：

```
1. 打开浏览器，访问前端地址
   URL: http://localhost:{frontendPort}

2. 截图记录初始状态
   → 保存截图到 {storyDir}/verification/round-{n}-step-{m}.png

3. 按验收标准逐条操作：
   a. 找到功能入口（按钮/卡片/菜单）
   b. 执行操作（点击/输入/选择）
   c. 截图记录操作后状态
   d. 判断是否符合预期

4. 记录验证结果：
   ├── 通过 → 标记 ✅
   ├── 失败 → 记录 Bug（截图 + 描述）
   └── 异常 → 记录错误（控制台日志 + 网络请求）
```

**验证要点**：
- 正常路径：按验收标准逐条操作验证
- 边界参数：输入边界值（空内容、超长内容、特殊字符）
- 异常路径：未登录、网络错误、权限不足
- 交互细节：加载状态、错误提示、成功反馈

### 3.3 接口自主验证

**可用工具**：
- `Bash` — 执行 curl 命令
- `mcp__MySQL-*` — 数据库查询验证

**验证流程**：

```
1. 获取接口清单（从研发设计文档）

2. 逐条验证接口：
   a. 构造请求（URL + Method + Headers + Body）
   b. 执行请求
   c. 检查响应（状态码 + 响应体 + 响应时间）
   d. 验证数据库变更（如适用）

3. 记录验证结果
```

**curl 验证示例**：
```bash
# GET 请求
curl -s -w "\nHTTP_CODE:%{http_code}" \
  -H "Authorization: Bearer {token}" \
  http://localhost:8080/portal/stickyNote/listing

# POST 请求
curl -s -w "\nHTTP_CODE:%{http_code}" \
  -X POST \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {token}" \
  http://localhost:8080/portal/stickyNote/add

# 数据库验证
mysql -u root -p -e "SELECT * FROM sticky_note WHERE user_id = 'test';"
```

### 3.4 Bug 记录格式

发现问题时，记录到 `context.json` 的 `verification.bugsFound`：

```json
{
  "bugsFound": [
    {
      "id": "BUG-001",
      "round": 1,
      "severity": "high|medium|low",
      "type": "functional|ui|api|data",
      "title": "便签创建后未自动刷新列表",
      "description": "点击新建便签后，列表未自动更新，需手动刷新页面",
      "reproduceSteps": [
        "1. 打开便签弹窗",
        "2. 点击新建便签",
        "3. 观察列表是否自动刷新"
      ],
      "expectedResult": "新建便签后列表自动显示新便签",
      "actualResult": "列表未刷新，需手动刷新页面",
      "screenshot": "verification/round-1-step-3.png",
      "status": "open"
    }
  ]
}
```

## 步骤 4：统一修复 Bug

当一轮验证完成后，如果有未通过的 Bug，进入修复阶段：

### 4.1 Bug 分析与分类

| 分类 | 修复策略 |
|------|---------|
| 功能性 Bug（逻辑错误） | 修改代码逻辑 |
| UI Bug（样式/交互问题） | 修改前端组件 |
| API Bug（接口错误） | 修改后端 Controller/Service |
| 数据 Bug（持久化问题） | 修改数据库操作或 SQL |

### 4.2 修复执行

1. 逐条分析 Bug 根因
2. 制定修复方案（必要时向用户确认）
3. 执行代码修改
4. 后端编译验证（IDE MCP `build_project`）
5. 标记 Bug 为 `fixed`

### 4.3 修复记录

```json
{
  "bugsFixed": [
    {
      "bugId": "BUG-001",
      "fixDescription": "在 addNote 方法中，创建成功后调用 loadNotes() 刷新列表",
      "filesModified": ["src/tools/sticky-note/composables/useStickyNote.ts"],
      "fixedAt": "2026-07-01T11:00:00+08:00"
    }
  ]
}
```

## 步骤 5：重启项目与下一轮验证

### 5.1 重启后端

**优先使用 IDE MCP**：
```
mcp__jetbrains-idea__execute_run_configuration → 重启项目
```

**备选方案**：
```bash
# 杀掉旧进程
kill {backendPid}
# 重新启动
cd {backendProjectPath} && mvn spring-boot:run &
```

### 5.2 确认前端热更新

前端通常支持热更新（HMR），无需重启。确认：
- 浏览器自动刷新或手动刷新页面
- 新功能代码已生效

### 5.3 进入下一轮验证

- `verification.currentRound` +1
- 重新执行步骤 3
- 验证所有之前失败的 Bug 是否已修复
- 检查是否有新引入的 Bug

## 步骤 6：验证通过标准

| 条件 | 说明 |
|------|------|
| 所有验收标准通过 | 需求文档中的每条验收标准都已验证 |
| 无 high/medium Bug | 只允许 low 级别的遗留 Bug（需标注为技债） |
| 边界场景处理正确 | 空值、超长、特殊字符等边界情况正常 |
| 异常场景处理正确 | 未登录、网络错误等有正确提示 |

## 完成后更新

- `context.json`：
  - `currentPhase = 总结`
  - `phases.功能自验证.done = true`
  - `verification.status = "passed"`
  - `verification.lastVerifiedAt = 当前时间`
- 驾驶舱 HTML：追加验证报告到修改记录
- 创建 `verification/` 目录存放截图

---

## 跳过条件

| 条件 | 处理 |
|------|------|
| 用户拒绝启动 | `phases.功能自验证.skipped = true`，进入总结 |
| 项目无法启动 | 记录原因，跳过验证，标注为已知限制 |
| 无浏览器工具可用 | 降级为纯接口验证 |
| 无 IDE MCP 可用 | 使用命令行启动后端 |

---

## 注意事项

1. **多模态模型提醒**：浏览器验证需要截图分析，务必提醒用户切换
2. **截图保存**：每步操作后截图，保存到 `verification/` 目录
3. **Bug 截图**：发现问题时截图记录，作为 Bug 证据
4. **用户干预**：遇到无法自动解决的问题，暂停并询问用户
5. **轮次上限**：建议最多 5 轮，超过后暂停并报告给用户
6. **环境清理**：验证完成后，询问用户是否停止项目进程
