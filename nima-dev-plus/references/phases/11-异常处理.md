# 异常处理与恢复

## 核心原则：不猜测、先确认、可恢复

当出现任何异常或不确定情况时，遵循以下优先级：

1. **不猜测** — 遇到不确定的信息，禁止编造或假设。宁可中断提示，不做武断臆想决策
2. **先确认** — 主动向开发者描述异常现象和你的分析，请求确认后再继续
3. **可恢复** — 优先利用已有文档和 `context.json` 自主恢复进度，减少重复劳动

## 通用异常场景处理

| 异常场景 | 表现 | 处理策略 | 沟通模板 |
|---------|------|---------|---------|
| 需求描述模糊 | 用户说"改个东西"但未指定具体位置 | 列出理解和可能的改动点，请用户确认 | "我理解您想修改的功能涉及...可能影响的文件有...请确认是否正确？" |
| 用户描述与代码不一致 | 用户说的方法名/类名/路径与实际不符 | 展示实际代码位置，说明差异并请求澄清 | "您提到的 `{用户描述的类}.{方法}()` 实际位于 `{实际类}.{实际方法}()`，请确认是否修改此处？" |
| 多个可能实现方案 | 一个需求有多种可行方式 | 列出各方案的优缺点和影响范围，请求决策 | "该需求有两种实现方式：1）{方案A} 2）{方案B}，您倾向于哪种？" |
| 缺乏领域知识 | 不熟悉业务逻辑或数据含义 | 说明已理解的部分和不确定的点，请求补充 | "以下是我对该业务流程的理解：...但以下几个点需要您补充：..." |
| 跨系统/外部依赖 | 改动涉及外部系统接口 | 说明依赖范围和假设前提，请求确认 | "该改动依赖 {外部系统} 的 {接口}，我假设返回格式为 {...}，是否准确？" |
| 权限/安全不确定 | 不确定是否需要特定权限 | 暂停操作并说明原因，请求确认 | "该操作涉及 {具体操作}，可能需要 {权限描述}。请确认是否可以执行？" |
| 数据库结构不明 | 需要的表或字段不存在 | 使用 MCP 工具确认，失败则请求用户提供 DDL | "我查询了 {表名} 的结构，未找到 {字段名}。请确认是否需要新增？" |
| 多阶段遗留待办 | 上一阶段的 TODO 未完成 | 识别遗漏项，展示影响，请求处理或标记延期 | "当前阶段发现以下遗留项：...请确认：1）现阶段补充 2）标记延期" |
| 用户否决分析结果 | 用户说"不是这样的"但未给出正确答案 | 记录被否定的点，询问正确方向 | "以下是我被否定的理解：...请问正确的应该是？" |

## 工具执行异常处理

| 异常场景 | 处理策略 |
|---------|---------|
| 数据库 MCP 查询失败 | 提示用户检查数据库连接配置，或手动提供表结构信息 |
| 文件读取/写入失败 | 检查路径是否存在、权限是否足够；无法解决时提示用户手动操作 |
| 编译/构建失败 | 展示完整错误日志，分析可能原因，请求协助定位 |
| Git 操作失败 | 展示冲突详情，说明原因；不擅自执行 --force 或覆盖性操作 |
| 模板文件缺失 | 使用技能中内联的模板格式继续工作，同时提示用户模板缺失 |
| MCP 工具不可用 | 降级为手动分析：请用户提供表结构截图、接口文档或代码片段 |

## 状态恢复指引

当会话中断、超时或需要恢复工作时，Agent 应按以下流程自主恢复：

### 步骤 1：读取 context.json 判断当前进度

```
如果 context.json 存在：
  ├── 解析 currentPhase 和各 phases 的 done 状态
  ├── 检查各已完成阶段的 output 文档路径是否有效
  └── → 进入步骤 2

如果 context.json 不存在：
  ├── 检查 story 工作区目录是否存在
  │   ├── 存在 → 扫描目录下所有文档，推断当前状态
  │   └── 不存在 → 告知用户"未找到工作进度文件，是否需要重新初始化？"
```

### 步骤 2：读取已产出文档，构建上下文

```
根据 phases 中标记为 done 的阶段的 output 路径：
  ├── 逐一读取对应的文档文件
  ├── 摘要关键信息：需求目标、设计决策、已完成的 TODO、遗留风险
  └── → 构建恢复上下文后进入步骤 3
```

### 步骤 3：根据 currentPhase 确定恢复点

| `currentPhase` | 恢复操作 |
|---------------|---------|
| `筑基` | 检查 projectEnv.detected，如已探测则摘要环境信息请用户确认；否则重新执行筑基 |
| `执行修改` | 检查 S-执行修改文档是否存在 → 存在则展示已完成的段落，从最新段落继续 |
| `需求澄清` | 检查 1-需求澄清文档是否存在 → 存在则展示需求摘要确认 |
| `现状分析` | 检查 2-现状分析文档是否存在 → 存在则摘要分析结论确认 |
| `研发设计` | 检查 3-研发设计文档是否存在 → 存在则摘要设计方案确认 |
| `原型确认` | 检查 3P-原型确认文档是否存在 → 存在则展示原型确认状态 |
| `开发交付` | 读取 todos 检查完成状态 → 有记录则展示未完成清单；无记录则从第1轮开始 |
| `闭环反馈` | 检查第4轮风险报告和遗留 TODO → 展示待确认项清单 |
| `总结` | 检查上一版总结文档 → 展示功能快照确认 |
| `归档交付` | 检查 branch 和提交状态 → 展示交付摘要确认 |

### 步骤 4：向用户展示恢复报告

```
┌─ 工作恢复报告 ─────────────────────────────────┐
│                                                  │
│  需求：{storyNameCN}                             │
│  模式：{mode} / {devMode}                        │
│  当前阶段：{currentPhase}                        │
│  当前迭代：第 {currentIteration} 轮              │
│                                                  │
│  已完成阶段：                                     │
│    ✅ {phase1} → {outputDoc1}                   │
│    ✅ {phase2} → {outputDoc2}                   │
│                                                  │
│  待完成：{待办摘要}                               │
│                                                  │
│  请确认是否从当前阶段继续？                       │
│  [1] 继续 — 从 {currentPhase} 阶段继续工作       │
│  [2] 回退 — 回退到上一阶段重新检查               │
│  [3] 重置 — 清除进度，重新筑基                   │
└──────────────────────────────────────────────────┘
```

## 各阶段异常处理补充

### 筑基阶段异常

| 场景 | 处理方式 |
|------|---------|
| 读取记忆但用户否认 | 执行完整探测，不假设记忆仍准确 |
| 探测结果为空（无 pom.xml） | 提示用户手动提供项目环境信息 |
| 前端检测结果模糊 | 向用户展示检测到的可能前端目录，由用户确认 |
| 用户无法确定模式 | 按当前已知信息推荐一种模式，标注"可在执行中升级/降级" |

### 现状分析阶段异常

| 场景 | 处理方式 |
|------|---------|
| 数据库表结构无法确认 | 标记为 `[异常]` 风险，请用户提供 DDL 或截图 |
| 关键代码路径跳转复杂 | 使用流程图或伪代码梳理调用链，展示给用户确认 |
| 发现已有 Bug 但不属本次范围 | 记录到 TODO 的 `[技债]` 分类，不擅自修复 |

### 开发交付阶段异常

| 场景 | 处理方式 |
|------|---------|
| 编译失败 | 完整展示错误、根因分析和修复路径，确认后修改 |
| 设计文档与实现矛盾 | 暂停实现，回到研发设计阶段更新设计文档 |
| 引入新依赖 | 按 coding-standards.md 说明原因、替代方案和影响，经确认后引入 |
| 多轮迭代中发现范围扩大 | 展示新增范围，请用户确认是当前需求包含还是新需求 |

### 需求内迭代异常

| 场景 | 处理方式 |
|------|---------|
| 迭代功能超出轻量范围 | 建议拆分为新需求空间 |
| 迭代导致已有功能回归 | 暂停迭代，先修复回归问题 |
| 多次迭代后需求空间过于庞大 | 建议归档当前需求空间，新建需求空间继续 |
